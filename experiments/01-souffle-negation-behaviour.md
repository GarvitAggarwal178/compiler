## STOP — escalation (read this first)

Per CLAUDE.md §5, three independent conditions fire on this probe:

1. **"Observed behaviour contradicts a blueprint claim. Example: Soufflé transforms
   P3."** — this is the literal worked example in CLAUDE.md, and it happened. On P3,
   Soufflé's `--magic-transform=*` produced a genuine magic seed
   (`@magic.p.{bf}(1)`, measurement `probe0-p3-on-extract`) for `p`, whose body
   contains the negated literal `!s(z)`. The adorned rule is:

   ```
   p.{bf}(x,y) :- @magic.p.{bf}(x), p.{bf}(x,z), !@neglabel.s(z), base(z,y).
   ```

   This is exactly the shape `docs/dlc-blueprint.md` §6 says Balbin et al. avoid by
   construction and §11's Prior Art Register says Soufflé's documentation declines to
   do. On this probe it happens on **both** negation programs, P2 and P3 — not once.

2. **"The transform pessimizes: `T_magic > T_base` on any program."** On P1,
   `T_magic` (1,525,848) is *larger* than `T_base` (1,525,796) — see
   `probe0-p1-off-extract` / `probe0-p1-on-extract`. This is a distinct failure mode
   named in blueprint §9.2, triggered on the very first program measured.

3. **A measured integer differs from the blueprint's stated expectation by more than
   one order of magnitude.** Blueprint §12 P1: "the ratio is ~10^3, not ~2." Measured
   ratio `T_base(P1)/T_magic(P1)` ≈ **0.99997** (measurement IDs above).

All three trace to one mechanism, not three bugs: `path` in P1 is declared
`.output`, so Soufflé must fully materialize it regardless of what any downstream
query demands — the magic-restricted computation (`@interm_out.path.{bf}`, 50 tuples,
correctly reduced) runs *in addition to*, not *instead of*, the full one. That
mechanism does not explain P2/P3, where no analogous unconditional output forces the
negated relation's full materialization; there, Soufflé transformed `unreach` and `p`
outright and still produced bit-identical answers.

**What I tried:** re-derived every number twice (rounded `souffleprof -c rel` text
table, then the underlying JSON profile log for exact integers — they agree);
confirmed determinism (fixture SHA-256 stable, `gen_p1_graph` idempotent under the
same seed); confirmed the three answer relations are byte-identical between magic-off
and magic-on (`probe0-p1-diff`, `probe0-p2-diff`, `probe0-p3-diff`) — the transform is
*sound* on all three probes, it just is not the win the blueprint predicts, and it
actively touches negation the blueprint says it won't touch.

**Three live explanations, not mutually exclusive:**

- **(a) Version drift.** Whatever documentation the Prior Art Register cites may
  describe an older Soufflé. The `@neglabel.<rel>` mechanism observed here (present
  only when `--magic-transform=*` is combined with negation) looks like Soufflé
  already implements something in the shape of Balbin's per-literal safety segment
  internally. If so, Q3 ("does *Extended Magic for Negation* ship an artifact?") may
  be moot — Soufflé itself may already be that artifact, undocumented as such.
- **(b) Soufflé is already selective, not blanket-permissive.** Both negated
  relations transformed here (`unreach` in P2, `p` in P3) negate a predicate that does
  *not* depend on the magic seed driving the transform (`reach` and `s`/`base`
  respectively). That is close to what the blueprint's own guard clause (b) is meant
  to detect as safe. If Soufflé is already doing guard-equivalent case selection
  silently, the project's headline (a guard Soufflé lacks) needs a program where
  Soufflé's selection is *wrong*, not one where it merely exists.
  This is not a coincidence I can subject to my own two-attempts credit here: it
  needs a program built specifically to distinguish "Soufflé transforms every
  negation" from "Soufflé transforms only the safe shapes" — that is a design
  decision about the M3 corpus, not a Phase 0 finding.
- **(c) P3-specific: the culprit-cycle mechanism never formed.** Soufflé's own
  optimizer inlined `q(x,y):-base(x,y)` away before magic-transform ran — confirmed by
  reading the post-transform rule bodies, which reference `base` directly, never `q`
  (`probe0-p3-on-profile`). `q` never exists as a materialized, magic-transformable
  relation in Soufflé's IR for this program, so the blueprint's named mechanism
  (`magic_q →¬ s → q → magic_q`) cannot close — there is no `q` or `magic_q` to close
  it through. This explains P3 specifically; it does not touch P2, which has no
  inlining candidate and still transformed cleanly.

**Cheapest experiment to distinguish (a)/(b) from (c), not yet run:** `souffle
--inline-exclude=q -m '*' -p prof_on_noinline.log p3.dl`. `--inline-exclude` exists
(`souffle --help`, confirmed). If `q` survives as a materialized relation and Soufflé
*still* transforms `p` cleanly, (c) is ruled out as the explanation for P3 and (a)/(b)
carry more weight. If forcing `q` to exist changes the outcome (decline, or a wrong
answer), (c) was the story for P3 specifically and P2 needs its own explanation.

I have not run this — it is outside Phase 0's six measurements and changes the
corpus-selection question CLAUDE.md §5 reserves for a human decision ("Anything that
would change ... the pre-registered corpus subdirectory"). Stopping here.

## What did not work / remains unverified

- `souffleprof -c rel`'s text table rounds to 3 significant figures ("1.52M"); every
  exact integer in this report instead comes from parsing the underlying JSON profile
  log directly (`harness/parse_profile.py`), cross-checked against `wc -l` on the
  `.output` CSVs where one exists. The two methods agreed everywhere they overlap.
- The "total derived tuples" metric is not well-defined once a magic-transformed
  program contains a `COPY_T` relation (like `path` in P1, a rename/copy of
  `@interm_out.path.{ff}`) — is a copy a derivation? I excluded copies from the sums
  in `docs/MEASUREMENTS.md` and said so; a hostile reader can reasonably argue the
  opposite convention. This needs a definition pinned down before M2, not invented
  per-report.
- P2's numbered check (does Soufflé decline negation transforms) is not one of the
  six required answers but was run anyway (`probe0-p2-*`) because it is Q1 in the
  blueprint's open-questions table. It reinforces the P3 finding rather than
  complicating it.
- I did not attempt to explain the `@neglabel` naming or confirm it against Soufflé
  source — CLAUDE.md's Prior Art Register entry says "cite, do not read the source."
  The mechanism is inferred entirely from profiler/log output, not from reading
  `MagicSet.cpp`.
- A skeptic's first move: ask whether P1's `.output path` was a mistake in my
  transcription. It was not — verified against `docs/dlc-blueprint.md` §12 verbatim
  (`.output path` is present in the source block). It is a property of the probe
  program the blueprint specifies, not a harness bug.

Three sentences: P1's answer is unchanged and larger in derived-tuple count under
magic, because `path` is a required `.output` and gets computed twice (restricted and
unrestricted). P2 and P3 both show a real reduction with a bit-identical answer, but
both do it by transforming a relation whose body negates another relation — the
scenario the blueprint's guard exists to gate, applied here by Soufflé with no visible
gate. All three probes agree on one point without exception: every answer relation
Soufflé produced under `--magic-transform=*` is byte-identical to the untransformed
answer.
